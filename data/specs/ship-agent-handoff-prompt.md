## 【1 ｜ 共同需求來源與參考背景】
1. **核心需求來源**：本對話隨附之《青年局 AI 實戰營小組開發工作包》與《DEMO 主題確認模板》。
2. **學術與技術背景**：依據國艦國造近期參考的國際公約 **S1000D Issue 6.0 規範**，船舶技術文件具有高度複雜性與嚴謹度，包含：
   - 結構分為：`<identAndStatusSection>` (識別與狀態區塊，包含唯一 DMC 編碼、適用性、版本) 與 `<content>` (內容區塊，使用 `<description>` 與 `<levelledPara>` 進行多層級嵌套)。
   - 表格標準化：必須精準提取欄寬 `colwidth="XXmm"`、並生成 `<colspec>`、`<thead>`、`<tbody>` 的結構化 XML 實體。
   - 核心限制：傳統 4B 等輕量級本地模型在處理多頁（5頁以上）技術文件時，容易因 2048 token 上下文限制與 RAG 語義嵌入精度不足，導致符合度斷崖式下滑。因此，本第一版原型在正式環境中，建議使用高效能大模型（如 Claude 或 GPT-4 API），以確保高精準度的文字比對與結構還原。
3. **優先順序**：正式企業命題與已標記為 Fact（事實）的內容優先；本提示詞中定義的規則為開發邊界；對於不確定或衝突的資訊，請主動提出詢問，不得自行猜測。

## 【3 ｜ 本組優先成果 (1 User × 1 Moment × 1 Input × 1 Output × 1 Metric)】
我們這一版原型最想證明的**核心假設**是：「如果系統能做到 100% 精準追溯差異（提供精確的頁碼與原文對照），第一線船舶維修人員就會完全信任 AI 的比對結果，從而解決傳統技術文件版本混亂與肉眼比對易漏的痛點。」

* **1 User (核心使用者)**：第一線船舶維修工程人員、技術管理與品質保證人員。
* **1 Moment (關鍵時刻)**：在準備執行船舶設備維修、檢修或安全檢查前，收到原廠或總部發布的新版技術文件，必須確認變更項目時。
* **1 Input (輸入資料)**：上傳兩個版本（新版與舊版）的模擬船舶技術文件 PDF/Word。
* **1 Output (輸出產物)**：一份結構化的版本差異報告。介面上需提供：
  - 兩版對照的差異表格（新增/刪除/修改項目）。
  - **重大安全變更警示**（如涉及壓力、溫度、耐壓數值、關鍵工安步驟的變更，須以紅色高亮標示）。
  - **高嚴謹度追溯性**：每項差異必須 100% 附帶【舊版頁碼+原文段落】與【新版頁碼+原文段落】的精準對照。
* **1 Metric (衡量指標)**：完成長篇技術文件（5-10頁）差異分析並標定安全變更的時間，**從人工肉眼比對的數小時，縮短至數分鐘以內**。

## 【4 ｜ Business / User / Stakeholders 組織對齊】
開發時請隨時牢記我們背負的組織绩效與各關係人的在意點，在 UI 與系統邏輯上做出對應的偏好設計：
* **Pain Owner (船舶維修工程人員)**：極度害怕漏看重大更新而承擔工安責任。因此，**UI 介面上「重大變更警示」必須極其顯眼，且不容許任何「自信猜測」**，若比對不確定應主動標示「請人工確認」。
* **KPI Owner (安全與品質主管)**：在意「關鍵安全變更漏看率 = 0%」與「船舶維修合規率 100%」。因此，比對引擎必須針對「數值變更」（如 10 bar 改為 12 bar）和「關鍵詞（警告、警告事項、Warning、Caution、禁止）」有極高權重的比對機制。
* **Budget Owner (技術長 CTO)**：在意預算合理性與長期投資報酬率 (ROI)。因此，第一版原型需呈現出極高的工作時間節省效益。
* **Data / IT Owner (技術管理部)**：在意技術手冊的數位化程度與 XML/PDF 排版一致性。

## 【5 ｜ Given ｜ 已知條件與開發邊界】
* **Agent 形式 (Form)**：一個簡約、直觀的單頁互動式網頁原型（Web-based App），可使用 Python (Streamlit / Gradio) 或 React+Tailwind 進行快速建置。
* **模擬資料 (Mock Data)**：由於船舶技術手冊屬於機密，我們首版將使用「5~10頁之模擬海巡艦艇建造與入級規範 2025」之新舊版 PDF 文件作為測試 Input。
* **系統生成參數設定**：為了確保 XML 結構與文字比對的事實嚴謹性，大模型的推理參數需設定為：
  - `Temperature = 0.5`（低隨機性，確保聚焦於事實與結構）。
  - `Top K Sampling = 40`。
  - `Repeat Penalty = 1.1` (避免產生重複的贅字，但不過度懲罰以防結構缺失)。
  - `Top P Sampling = 0.95`。
  - `Min P Sampling = 0.05`。
* **人工確認節點 (Human Approval)**：AI 產出的差異報告僅作為「草稿與警示輔助」，介面上必須提供「工程人員確認核取方塊」，由工程人員逐項確認（Approve / Disapprove）後，方可匯出為最終的「差異審查簽核 PDF/HTML」。
* **Out-of-Scope (本版不實作範圍)**：
  - 本版不要求對接真實的船隊 ERP/PMS 系統。
  - 本版不進行 100% 的 S1000D 數據模組自動化 XML 轉檔，但差異報告的追溯格式需參考 S1000D 的段落層級嵌套思想。

## 【6 ｜ Design ｜ 方案設計與核心工作流】
請依據以下 Before/During/After 工作流進行系統架構設計：

1. **Before (前置狀態)**：
   - 準備好 2 份模擬技術手冊 PDF (Old_v1.0.pdf / New_v2.0.pdf)。
   - 系統已載入 RAG 向量檢索或長文本比對引擎（可先將 PDF 進行文字與表格結構提取）。
2. **Trigger (觸發事件)**：
   - 使用者將新舊兩版 PDF 檔案拖入上傳區，點擊「開始版本差異比對」按鈕。
3. **During (處理中步驟)**：
   - **Step 1: 結構化提取**：使用 PDF 解析工具，將文字與表格按「頁碼、章節標題、層級段落 (levelledPara)」提取出來。
   - **Step 2: 差異比對 (Diff Engine)**：對比新舊版文本。必須能精準識別出：
     - **[新增]**：新版增加的段落或表格列。
     - **[刪除]**：新版刪除的內容。
     - **[修改]**：同一段落中，數值、零件料號、或關鍵步驟的變更。
   - **Step 3: 安全重大變更提取**：使用語義分析，過濾出包含「Pressure、bar、MPa、溫度、警告、危險、Warning、Danger」等關鍵字或數值變動的段落，並將其嚴重度標記為「Critical (紅色)」。
   - **Step 4: 影響範圍對照**：分析變更段落中所提及的設備名稱（如：泵浦、柴油機、配電盤），與系統設備對照表進行模糊匹配，指出可能受影響的船舶設備。
4. **After (結果呈現與接手)**：
   - 產出側邊雙欄或卡片流介面：
     - **左側**：安全警示與重大變更卡片。
     - **右側**：完整的版本差異比對表格（欄位：變更類型、舊版頁碼、舊版原文、新版頁碼、新版原文、影響設備、人工確認勾選）。
   - **Human Handoff (人工接手)**：第一線工程師閱讀後，在每條差異旁勾選「已確認」，並能點擊「導出差異審定報告 (HTML/PDF)」用於簽核。

## 【7 ｜ Proof & Acceptance ｜ 驗收情境】
請在程式碼中預留或建置以下四種測試情境，以利我們在 Demo Day 進行功能驗收：

1. **Normal Path (正常路徑)**：上傳兩版包含文字與標準表格的 PDF，系統在 1 分鐘內成功產出差異報告，且所有修改的數值（如 10 bar 變成 12 bar）皆能精確標示。
2. **Exception Path (例外/高風險路徑)**：當上傳的 PDF 包含「掃描檔（髒數據、無法選取文字）」時，系統不可直接崩潰，必須在 UI 上提出明確警示：「檢測到部分頁面為掃描圖檔，建議先進行 OCR 處理或人工雙重校對，以防漏看重大變更。」
3. **Missing Info (資訊不足路徑)**：若上傳的 PDF 缺少「版本號碼、修訂日期」等元數據，系統應暫停並在介面上彈出提示框，要求使用者手動輸入「舊版版本號」與「新版版本號」，方可繼續比對。
4. **Human Control (人工確認路徑)**：UI 介面上的核取方塊與導出按鈕功能完備。若有任何一項「Critical 重大變更」未被使用者勾選「已確認」，在點擊導出時，系統需彈出二次確認視窗：「您仍有重大安全變更未進行人工審查，確定要導出報告嗎？」

## 【8 ｜ Scope ｜ 版本開發範圍】
* **First Version (第一版 DEMO 核心)**：
  1. 雙 PDF 檔案上傳介面。

  3. 重大安全變更自動標紅警示（如：耐壓值變更）。
  4. 包含頁碼與原文的差異對照 UI 呈現。
  5. 匯出 Markdown/HTML 差異報告。
* **Parking Lot (後續迭代)**：
  - 100% 符合 S1000D 標準之 XML (descript.xsd) 原生解析。
  - 對接船隊的 IETM (互動式電子技術手冊) 檢索系統。
  - 歷史改版原因追溯（對接歷史案例資料庫）。

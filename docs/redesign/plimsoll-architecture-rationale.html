0核心原則（貫穿全案）

一句話確定性層決定「哪裡變／變什麼類型」（免 token、可稽核）；LLM 只做「語意解讀」；規則引擎＋人工擁有最終判定。LLM 永不是必要相依，也永不設定最終風險級。

這條原則同時滿足四個需求：#2 稽核可重現、#7 輕量可轉向、#8 不亂下因果斷言、以及成本可控。現行反面基線恰好違反它——把「分級」和「解讀」都丟給 LLM 逐筆呼叫。

讀 src/comparison.py、backend/main.py、src/ai_providers.py 後，對照需求 v3 最高優先四條，全部踩線：

需求現況判定

規模：Python ~1,395 LOC、前端 ~1,409 LOC（將棄），目錄深度 3，真正引擎僅 ~730 LOC。買到的是可跑 demo，不是可擴充地基。

2儲存架構：local-first ＋ 檔案化 ＋ DB 可選上游

經三輪演進定案：不架 DB、純檔案，且「沒 DB 存本地、有 DB 就灌入」。

三種本機格式的選型

選項對 append-only 稽核判定
Google Sheet需 OAuth＋雲端，等於提前引入 Drive（#5）；離線失效v1 不採；留 P5 上游
Excel .xlsx假 append：整檔重寫、開檔即鎖、崩潰全毀只當匯出視圖
txt / JSONL真 append（O_APPEND）、零相依、可 grep/diff、離線最穩真相來源
關鍵洞見因為稽核採 append-only、事件不可變、每筆帶唯一 event_id，同步到 DB 就變成「idempotent 往前補」的免衝突動作——事件日誌本身就是同步協定。
Layer 1 LocalStore（永遠在，離線可用，真相來源）
  review_events.jsonl (append-only ★) · session.json · differences.json · config/*.json
Layer 2 SyncTarget（可選、可插拔）
  Postgres / MySQL / SQLite檔 / 雲端 API   ← DB 是下游鏡像，非第二真相來源
Gateway
  append_event(): ①先寫 LocalStore＝commit點  ②SyncTarget 健康則 best-effort 寫穿
  flush_pending(): 讀未同步事件 → idempotent upsert

三態 tag（本機／未同步／已同步）由可覆寫的 sync_state.json sidecar 推導，絕不回改稽核日誌。DB 連線一律延遲背景探測、不影響啟動、失敗降級本機（§24）。

3稽核骨幹：append-only 事件模型（event-sourcing 精簡版）

結構性保證差異的覆核狀態不是欄位，是投影。改判＝追加一則凌駕事件，舊事件連同其 AI 初判、覆核人、時戳原封保留。「不可被覆寫遺失」不是靠紀律，是靠 schema 讓覆寫在物理上不可能。
{"event_id":"e-0002","difference_id":"D01","event_type":"HUMAN_REVIEW",
 "ai_risk_at_time":"High","ruleset_version":"v1","human_verdict":"CONFIRMED",
 "reviewer_name":"陳○○","approval_role_code":"TECH_SUPT",
 "approval_role_label_snapshot":"安全品質主管（Technical Superintendent）",
 "created_at":"2026-08-15T03:35:12Z","prev_event_id":"e-0001"}

防竄改：凍結前綴 hash 錨點（採用你的提案）

  • 格式/規則先寫死，讀檔即 validate_schema()，手改破壞結構當場被抓。
  • 只 hash 已凍結前綴 [0, offset)——相容 append-only 的合法成長；改到前綴＝竄改。
  • 錨點存別處（DB 優先，離線退本機 .integrity/）；灌 DB 前比對，不一致＝告警＋略過該 session＋隔離待人工，本機日誌照原樣保留（它本身是證據）。

事件寫入單寫入者序列化（asyncio.Lock + flush + fsync）。骨幹必落 P0——不可事後補，補的那一刻早期事件已遺失。

4核准角色 ＋ 可調分級規則

  • 覆核人拆兩欄：reviewer_name（自由文字）＋ approval_role_code（結構化）。
  • 角色用參考表非 enum：config/approval_roles.json，種子 DPA / TECH_SUPT / FLEET_MGR / OTHER，企業體系不同時增列免改程式；OTHER 另存 custom_role_label。
  • 門檻用版本化規則檔：config/rulesets/v{N}.json，調門檻＝新增版本檔（immutable），比對凍結 ruleset_version，讓「這筆 AI 初判是哪版規則產生」永遠可回溯。倉庫 JSON 只當出廠種子。
  • 核准權限：config/approval_policies（角色 × 可核准最高風險級）。
  • 覆核與簽核經事件關聯此二者，並存 approval_role_label_snapshot 快照——表改名不影響歷史稽核。

這一組取代寫死的 _risk_and_reason()；每條規則 when → then 是一個 Specification，命中即記可解釋來源（滿足 AC3）。

5雙頁碼 ＋ data_origin 三態（一級欄位）

  • 頁碼參照＝{pdf_page, print_label, label_source}；print_label 取自 PDF PageLabels，可為非數字（羅馬頁碼），抓不到則 NULL 且 label_source=unknown，不猜測。
  • 所有 API 回傳帶 data_origin ∈ {computed, ai_inferred, demo_seed}；前端見 demo_seed 掛「示範資料」tag，真實 session 禁未標記寫死值。

6Bedrock 協作 ＋ 分析模式 A/B/C（可切換）

「換模型會不會影響」取決於走哪條路線——因為影響的本質是「分級與判定由確定性程式產生，還是由模型產生」。

A · rules-first（預設）C · model-heavyB · model-only
誰定風險級規則引擎（確定性）模型模型
換模型影響極小：grades 可重現中大：grades 漂移最大：換模型＝換一套差異分級
稽核（#2）可重現需釘版本＋快照跨模型不可重現，治理風險
成本最低高最高
拍板不三選一，把界線做成 config knob analysis_mode，預設 A。整套介面化（LlmProvider Strategy＋Rules Engine），三模式同一套程式切設定即換。
  • 雙雲皆在範圍，Bedrock 先接、Vertex(Gemini) 次之（另留 OpenAI／local-rules）。每筆判定記 model_id＋版本＋provider＋analysis_mode。
  • 路由而非全送：只有「規則分不清」或「大改但無規則觸發」才送 LLM；批次 10–20 筆／請求。
  • 擷取/分類用低溫 0.0–0.2（現行 0.5 偏高易漂）；prompt 強制 abstention（證據不足回 needs_human=true，不杜撰）。
  • 現行 ai_providers.py 逐筆呼叫 LLM（25 筆＝25 次 round-trip）是要改的核心。

7異動判斷：偵測管線 Stage 0–4

Stage -1 頁面分類 → 掃描頁: OSS OCR(低信心才上雲) / 圖頁: 像素diff+實體抽取(+vision殘差)
Stage 0  正規化   NFKC + 全半形統一 + 去頁首頁尾頁碼 + CJK 斷詞
Stage 1  結構對齊 以章節碼/SFI/DMC/條號對齊條文；頁雜湊短路先跳過未變頁
Stage 2  確定性分類 數值/義務/安全詞/引用/適用範圍（規則可設定，命中即記可解釋來源）
Stage 3  LLM 語意 只處理「大改但無規則觸發」「規則分不清」→ 隱含/語意變更
Stage 4  人工覆核 最終判定，寫 append-only 事件
變動類型怎麼抓層級
數值/極限（85→80°C）數值+單位正規化後比對，最便宜最可靠確定性
內規/程序義務（每月→每週）義務詞＋頻率詞集合確定性
法規引用引用/條號/料號（CP-120、DMC）regex確定性
適用範圍scope 語句偵測確定性
隱含邏輯／語意改變「大改但無規則觸發」路由 → Bedrock 解讀LLM
OCR 路由子規則（圖片式文字貼在 PDF） 圖片是文字→OCR（OSS 先、低信心才上雲）；圖片是圖→像素 diff＋實體抽取，殘差才 vision；整份丟模型只當「OCR 失敗/純圖」的逐頁升級，非預設，輸出標信心、低信心導人工（AC4）。

低信心（對齊差、掃描歪斜、OCR 缺字、LLM abstain）→ 標「無法可信比對」導人工，不輸出未受支持結論（AC4）。

現行正確性 bugSequenceMatcher 以空白切 token，但中文沒有空白——CJK 條文會誤判。Stage 0 的 CJK 斷詞是必修，不是優化。

8規模與效能

維度舒適區上限訊號
同時比對一次一對（單人單機）多人 → 破壞單寫入者 → P5 DB-primary
每份頁數數百頁（秒級）上千頁 → 背景工作＋進度
檔案容量限制在文字密度非 MB；5MB/800 頁 OK50MB 純掃描 → 需 OCR
差異數量數百筆全送 LLM → 分鐘級＋$$；靠批次+路由壓下

瓶頸排序：LLM 呼叫數 ＞ diff 演算法 ＞ PDF 抽字 ＞ JSONL。上千頁 I/O 四招（按 CP 值）：

  1. 頁雜湊短路（最大槓桿）：兩版同 hash 的頁整頁跳過，1000 頁只改 12 頁就只處理 12 頁。
  2. PyMuPDF(fitz) 取代 pypdf（C-backed、快數倍，§6 光柵化也需要）。AGPL：demo/鐵人賽非閉源商用可接受，商用化再購授權
  3. 長工作背景任務＋進度回報（單人單機用 asyncio/thread，不引入 Celery/Redis）。
  4. 以章節切塊分段平行（ProcessPoolExecutor 繞 GIL）。

9省 token／提正確率的小工具

省 token（由大到小）

  1. 規則優先路由——多數變更本機判定，只殘差送 LLM。
  2. 只送變更片段＋最小上下文，不送整頁。
  3. 批次 10–20 筆／請求。
  4. 內容雜湊快取：sha256(old|new|ruleset_version|model_id) 命中重用，重跑 0 token。
  5. 正規化擋掉假 diff（去頁首頁尾、collapse 空白、忽略純重新分頁）。
  6. 純數值變更捷徑：只有數字變 → 規則直接輸出，根本不進 LLM。

提正確率（幾乎不耗 token）

  1. 依章節碼/條號結構對齊（最大槓桿，解決重新分頁假差異）。
  2. NFKC＋全半形統一＋CJK 斷詞（修中文 bug）。
  3. 數值+單位正規化（85 °C/85℃ 視為同一）。
  4. 表格列以主鍵欄對齊。
  5. 對齊分數門檻低 → 標低信心導人工。
  6. （選配、本機無 token）小型多語 embedding 對齊改寫/搬位的同一條文。

12特徵層 ＋ 稽核即標籤

特徵群例子

義務/程序obligation_added/removed、frequency_shortened、禁止詞

結構edit_distance、pct_changed、is_table_row、alignment_confidence
語意（殺手級）embedding_distance(old,new)——重用 e5-small、免 LLM token
飛輪殺手級特徵：embedding_distance 高 ＋ 無規則觸發 ＝ 送 LLM 的路由依據。而每筆人工判定（含誤報/風險改判）就是對特徵向量的標籤——跨 session 累積成 labeled data，日後訓小分類器（logistic/GBDT）降誤報、免 token 推論。競品拿不走你的海事覆核標註。v1 只做規則＋特徵，學習模型為後續（守 #7）。

14影響視圖：component_ref（SFI）＋ 2D，3D 延後

  • 橋樑＝資料掛鉤：affected 升級成結構化 component_ref，對 config/component_taxonomy.json。

16測試策略

現況：規格樹零測試；舊 Playwright 針對被棄用的 React UI，等於作廢。稽核是核心賣點，其不變式必須自動化、且落在 P0。

  • P0 pytest：規則引擎（text pair→預期風險）、數值/義務偵測、結構對齊、防竄改（改凍結行→前綴 hash 不符→quarantine）。
  • 稽核不變式（P0–P3）：append-only 永不 mutate；投影＝最後人工判定；AI_INITIAL 先於 HUMAN_REVIEW；同步 idempotent。用測試把 #2 釘死。
  • Golden 快照：拿 data/demo/*.pdf，純規則引擎（不呼叫 LLM）跑固定差異集擋回歸。
  • LLM 層：CI mock Bedrock，測 prompt/JSON/abstention/路由；絕不打真 API。
  • E2E Playwright（新 UI，綁 AC）：AC1 上傳、AC2 展開雙欄、情境四未覆核 High 攔截、持久化 journey（判定→重整→還在）、啟動獨立（無 DB 全流程可用）。全跑規則引擎確保 deterministic。

17靈魂質問：這專案解決到使用者問題嗎（誠實評估）

它真正解決的：頁碼可追溯的差異 ＋ 防竄改的人工覆核稽核軌跡（強、難仿）、分級可設定、不足就 abstain。

四個誠實缺口（規格 #7 已自認急迫性未驗證）：

  1. 「比對版本」是不是急迫的痛？未驗證。更深的痛可能是「沒人知道出了新版／哪份是現行版」——diff 預設使用者已有兩版且願意比。
  2. 文件現實：大量掃描/圖片，文字比對前提最脆弱（沒硬 OCR 就 garbage in）。
  3. 安全信任門檻：漏抓一個關鍵變更是災難級；人在迴路很誠實，但那是輔助不是取代。
  4. 導入摩擦：不綁 DMS（對可轉向對）＝手動餵 PDF，對忙碌工程師是採用殺手。
判斷架構是穩的，且刻意輕、可轉向——這正是「問題未驗證」該有的對沖。但架構替代不了客戶探索。最高 ROI 一步：問 2–3 個真實對象「今天怎麼比版本？哪裡卡？願不願貼 PDF？稽核軌跡對稽核/DPA/船級社值不值得付錢？」
定位（#7）稽核／簽核軌跡不作為單一主打，而是與差異偵測、100% 可追溯、可設定規則、輕量可轉向並列的「優點之一」。不背 BPMN 工作流引擎與 PKI 電簽的包袱——hash 錨定的 append-only 簽核事件即實務簽名（對內部 MoC 達電簽約 80% 價值）。

Plimsoll — 系統圖文手冊

船舶技術文件版本差異 Agent。核心承諾：確保執行者拿到正確、現行、完整的技術資料，並讓每一筆風險判定都可回溯到原文與覆核人。本手冊以圖表對照本輪確認的設計稿（ui-mockup-v3.2.html）與架構決策（architecture-decisions-A-B.md），供工程開發與跨角色溝通使用。

範圍：P0–P4 儲存：local-first，DB 為可選上游 稽核：append-only 事件日誌 最高風險：核心痛點急迫性未經產業驗證（OQ3）
01

C4 模型・情境圖（System Context）

Plimsoll 在誰的世界裡運作：使用者是誰、系統邊界在哪、外部依賴有哪些。LLM 與 OCR 皆為可切換／可停用的外部依賴，不是必要相依。

C4Context title Plimsoll 系統情境圖 Person(reviewer, "安全品質主管 / 維修工程師", "覆核差異並簽核匯出報告") System(plimsoll, "Plimsoll", "比對船舶技術文件版本差異，產生可稽核的覆核與簽核報告") SystemDb_Ext(localfs, "本機資料夾", "PDF 原始文件、JSONL 稽核日誌、設定檔（真相來源）") SystemDb_Ext(db, "資料庫（選用）", "PostgreSQL / MySQL / SQLite，下游鏡像，非必要") System_Ext(llm, "LLM 服務", "AWS Bedrock / GCP Vertex，僅語意解讀，不設定最終風險級") System_Ext(ocr, "OCR 服務", "本機 OSS 優先，雲端服務為殘差備援") Rel(reviewer, plimsoll, "上傳文件、覆核差異、簽核匯出") Rel(plimsoll, localfs, "一律先寫，真相來源") Rel(plimsoll, db, "選用同步，best-effort，事件冪等灌入") Rel(plimsoll, llm, "差異語意解讀，可切換/可停用") Rel(plimsoll, ocr, "掃描頁與工程圖頁文字擷取")
怎麼讀｜虛線外的三個外部系統都是「可選」或「可切換」：拔掉資料庫，系統仍完整運作；拔掉 LLM，退回本機規則引擎；拔掉雲端 OCR，退回本機 OSS 辨識。這是「輕量可轉向」原則在圖上的具體樣子。
02

C4 模型・容器圖（Container）

拆到「前端／後端／儲存／可插拔上游」四個容器，對應目前規劃的技術選型。

C4Container title Plimsoll 容器圖 Person(reviewer, "覆核人員") Container_Boundary(app, "Plimsoll 應用") { Container(spa, "前端 SPA", "React + Tailwind", "三欄對話式介面：來源、對話主線、覆核與匯出") Container(api, "後端 API", "FastAPI (Python)", "文件解析、差異比對、規則引擎、StorageGateway") ContainerDb(local, "LocalStore", "JSONL / JSON 檔案", "review_events.jsonl 等，append-only 真相來源") Container(sync, "SyncTarget Adapter", "SQLAlchemy Core", "可插拔上游：SQLite / Postgres / MySQL") } ContainerDb_Ext(db, "資料庫（選用）", "PostgreSQL 等", "下游鏡像，非第二真相來源") Container_Ext(llmp, "LlmProvider", "Bedrock / Vertex / 本機規則", "Strategy 介面，可切換分析模式 A/B/C") Container_Ext(ocrp, "OCR Provider", "Tesseract/PaddleOCR + 雲端備援", "分層 OCR 管線") Rel(reviewer, spa, "操作", "HTTPS") Rel(spa, api, "呼叫", "REST/JSON") Rel(api, local, "先寫即 commit", "檔案 I/O") Rel(api, sync, "best-effort 寫穿 / flush_pending", "SQLAlchemy") Rel(sync, db, "idempotent upsert by event_id", "SQL") Rel(api, llmp, "差異語意解讀", "SDK/API") Rel(api, ocrp, "掃描頁/圖頁擷取", "SDK/API")
怎麼讀｜注意 SyncTarget Adapter 夾在後端與資料庫之間——換任何一種資料庫品牌，只是換這一個 adapter，前端與核心後端邏輯完全不動，這就是 §7「輕量可轉向」在架構上的體現。

08

狀態圖（共三張）

分別對應「一次比對工作階段怎麼推進」「一筆差異的覆核判定怎麼變化」「儲存要不要同步到資料庫」三個獨立但常被混在一起討論的狀態機。

08.1　Session 進度狀態機

stateDiagram-v2 [*] --> 載入來源 載入來源 --> 待補件: 缺版本號或掃描頁信心不足 待補件 --> 載入來源: 人工補填後重新檢查 載入來源 --> 差異比對: 版本號與頁碼皆齊全 差異比對 --> 逐項覆核: 產生候選差異與風險等級 逐項覆核 --> 逐項覆核: 每筆判定為追加事件，互不影響 逐項覆核 --> 簽核匯出: 點擊匯出 簽核匯出 --> 修訂草稿匯出: 仍有 High 未覆核，且人工勾選確認 簽核匯出 --> 正式匯出: 全部 High 已覆核 修訂草稿匯出 --> [*] 正式匯出 --> [*]
怎麼讀｜這張對應右欄底部的四個流程節點（載入來源／差異比對／逐項覆核／簽核匯出）。唯一的分岔在最後一步：有沒有「修訂草稿」警示，取決於還有沒有 High 未覆核，而不是取決於使用者想不想匯出。

08.2　差異覆核判定狀態機

stateDiagram-v2 [*] --> AI_INITIAL: 比對完成，系統產生候選風險 AI_INITIAL --> CONFIRMED: 人工判定「已確認」 AI_INITIAL --> TRACKED: 人工判定「需追蹤」 AI_INITIAL --> REJECTED: 人工判定「不採納」 CONFIRMED --> TRACKED: 追加新事件改判 CONFIRMED --> REJECTED: 追加新事件改判 TRACKED --> CONFIRMED: 追加新事件改判 TRACKED --> REJECTED: 追加新事件改判 REJECTED --> CONFIRMED: 追加新事件改判 REJECTED --> TRACKED: 追加新事件改判 AI_INITIAL --> [*]: 若為 High，匯出時觸發 UnreviewedExportGuard CONFIRMED --> [*]: 視為已覆核，可正常匯出 TRACKED --> [*]: 視為已覆核，可正常匯出 REJECTED --> [*]: 視為已覆核，可正常匯出
怎麼讀｜箭頭再多都只是「表面狀態」，底層永遠是追加事件，不是覆寫欄位——CONFIRMED 改判成 TRACKED，實際上是多寫一行 review_events.jsonl，舊的 CONFIRMED 事件仍然留著，供稽核回溯「誰在什麼時候把已確認改成需追蹤」。唯一會擋下匯出的狀態是 AI_INITIAL（人工完全還沒判定過）。

08.3　儲存三態與完整性隔離

stateDiagram-v2 [*] --> 本機: 未設定同步或從未同步 本機 --> 未同步: 設定同步後產生新事件 未同步 --> 已同步: flush_pending 成功送達 已同步 --> 未同步: 本機再產生新事件 未同步 --> 隔離: 完整性驗證失敗（前綴 hash 不符） 隔離 --> [*]: 人工處置（下載原始日誌／標記已知悉）
怎麼讀｜這張跟上面兩張的差異在於：它描述的是「資料庫同不同步」，不是「這筆差異對不對」——即使一筆差異的覆核狀態是 CONFIRMED，它所屬的 session 仍然可能是「未同步」。兩個狀態機互相獨立。「隔離」是唯一不會自動恢復的狀態，系統不做自動修復，永遠等待人工處置。
09

使用者情境模擬

五個具代表性的操作情境，涵蓋正常路徑、缺件補流程、匯出攔截、低信心判讀與完整性風險。

情境 A

正常路徑：從上傳到簽核匯出

陳○○・安全品質主管，登入身分＝安全品質主管；核准角色＝船舶技術監督

  • 選擇本機資料夾，一次帶入主機冷卻系統維修程序 v1.0 與 v1.1 兩份 PDFAC1
  • 系統顯示文件名稱／版本／日期／適用設備，皆齊全，直接進入比對
  • 比對完成，產生 25 筆差異，其中 4 筆 High，Agent 於對話中列出重大變更摘要AC3
  • 陳○○逐項開啟 DiffCard，對照雙欄原文與雙頁碼，一一標記已確認／需追蹤AC2
  • 全部 High 覆核完成後點擊匯出，未跳出攔截，直接進入簽核表單
  • 選擇核准角色「船舶技術監督」，填入審查日期與報告編號，下載 DOCX 審查報告
結果：報告不含任何未覆核警示，25 筆差異全部附雙版本、雙頁碼、原文，稽核軌跡完整寫入本機。
情境 B

缺件補流程：抓不到新版版本號

維修工程師，登入身分＝維修工程師

  • 從本機資料夾挑了兩份 PDF，其中新版檔名未含版本號
  • Agent 在對話中主動提出「新版文件缺少版本號碼」，不自行猜測AC4
  • 右欄來源卡出現「手動輸入新版版本號」必填欄位，比對按鈕維持 disabled
  • 同時偵測到新版 p.5 為疑似掃描頁，文字層不足，一併於對話中提出
  • 工程師補填版本號 v1.1 後，比對按鈕才轉為可點擊
結果：系統不接受推測版本，直到人工補齊關鍵資訊才放行比對，避免報告建立在不可靠的版本基礎上。
情境 C

搶先匯出被攔截：仍有 High 未覆核

陳○○・安全品質主管

  • 比對出 25 筆差異、4 筆 High，陳○○只覆核了 22 筆便直接點擊「匯出」
  • 系統彈出 UnreviewedExportGuard，逐項列出剩餘 2 筆 High（D01、D07）及其風險內容情境四
  • 陳○○選擇「先去覆核這 2 項」，回到 DiffCard 完成判定
  • （替代路徑）若選擇仍要匯出，必須先勾選「我已知悉此報告將標為修訂草稿」，確認按鈕才會從 disabled 轉為可點擊
  • 匯出的報告封面自動加註「修訂草稿」警示與未覆核清單
結果：系統不會靜默放行未覆核的重大風險項，任何跳過覆核的匯出都會被明確標記，責任可追溯到簽核人。
情境 D

低信心判讀：工程圖頁的視覺差異（P8，示意）

陳○○・安全品質主管

  • 新版文件 p.2 為水路圖工程圖頁，像素比對定位出 3 處變更區塊
  • 系統標示「視覺差異為輔助判讀，信心度標為中」，並說明變更區塊由像素比對產生（客觀），但內容解讀由 AI 視覺模型推測AC4
  • 陳○○對照左右滑桿比對同一位置的新舊版原圖，確認新增迴流閥 V-102
  • 覆核判定「已確認」，並在覆核理由填寫「已同步更新每週保養排程表」
結果：AI 只負責定位「哪裡變了」，不對「變得好不好」下結論；最終判定必須人工完成。此情境對應 P8，本輪 P0–P4 暫不實作，僅供理解未來設計方向。
情境 E

完整性驗證失敗：稽核日誌疑遭手動修改

系統背景行為 + 覆核人員後續處置

  • 「壓載水處理系統手冊」比對紀錄嘗試 flush_pending 同步到資料庫
  • 系統比對凍結前綴 SHA-256 錨點，發現與目前檔案內容不符
  • 系統自動判定為 隔離：不灌入資料庫、不刪改本機檔案，於「設定 → 資料來源」顯示完整性告警
  • 使用者可選擇「下載原始稽核日誌」交付人工比對，或「標記為已知悉並結案」（不影響本機原始檔案）
結果：系統對可能遭竄改的稽核紀錄採取「隔離不處理」而非「自動修復」，把處置權完全留給人工，避免竄改被系統自動掩蓋。
